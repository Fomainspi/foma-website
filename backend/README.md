# FOMA Backend (New, From-Scratch Serverless Stack)

This directory contains a brand-new AWS SAM project implementing the FOMA
bootcamp registration backend, built independently of the existing legacy
`bootcamp-registration` Lambda/API Gateway/database. The legacy system is
**not modified, deleted, migrated, or depended upon** by anything here; it
remains available as a rollback path until a future Production cutover is
explicitly approved.

## Architecture

```
Frontend (dev.foma.life / foma.life)
        |
        v
API Gateway (HTTP API, generated endpoint, per-environment)
        |
        v
Lambda: foma-register-<env>  (Node.js 20.x)
        |
        v
DynamoDB: foma-registrations-<env>  (on-demand)
        |
        v
Amazon SES (admin notification + optional student confirmation)
```

Every resource name is suffixed with `-dev` or `-prod` (`EnvironmentName`
parameter), and **each environment is deployed as its own separate
CloudFormation stack** (`foma-backend-dev`, `foma-backend-prod`). This is
the mechanism that guarantees isolation:

- The Dev Lambda's IAM role is generated by SAM's `DynamoDBWritePolicy`
  scoped to exactly the Dev table's ARN. It has no statement referencing
  the Production table, because the Production table doesn't exist in the
  Dev stack at all.
- The SES `ses:SendEmail`/`ses:SendRawEmail` permission is scoped to the
  specific verified sender identity ARN configured for that environment
  only (`SesSenderEmail` parameter), so a Dev deployment cannot send mail
  "From" a Production identity or vice versa.
- There is no cross-stack reference, shared table, shared Lambda, or
  shared IAM role between Dev and Production. Deploying Production later
  will create a **second, completely independent stack** from the same
  template with different parameter values.

## Files

- `template.yaml` — AWS SAM template. Parameterized by `EnvironmentName`,
  `AllowedOrigin` (CORS), `SesSenderEmail`, `SesAdminRecipientEmail`, and
  `SesAllowedTestRecipients`. Deploying it twice (once per environment)
  produces two fully isolated stacks.
- `src/functions/register/index.mjs` — Registration Lambda handler:
  validates input, computes the enrollment `score` **server-side** from
  `experience` (a client-supplied score is intentionally ignored to
  prevent tampering), writes the registration to DynamoDB, sends the
  admin notification email to a fixed, server-configured address (never
  a client-supplied `notifyEmail`), and optionally sends a student
  confirmation email.
- `src/functions/register/package.json` — Lambda dependencies (AWS SDK v3
  clients for DynamoDB and SES).
- `samconfig.toml` — SAM CLI deployment configuration. Only a `[dev]`
  environment section is defined for now, so a plain `sam deploy` cannot
  accidentally target Production. A `[prod]` section will be added only
  once Dev has been tested and explicitly approved.
- `events/register-event.json` — Sample API Gateway HTTP API v2 proxy
  event for local testing with `sam local invoke`.

## Dev-only SES safety guard

While testing in Dev, the optional student confirmation email is only
sent if the student's email address appears in the
`SesAllowedTestRecipients` parameter (a comma-separated allowlist of
SES-verified addresses). Any other address is skipped (logged, not
sent) even if `sendConfirmation: true` is in the request — this prevents
accidentally emailing arbitrary external addresses while SES is in
sandbox mode or during early testing. The admin notification email
always goes to the fixed `SesAdminRecipientEmail`, which must itself be
a verified address while SES is in sandbox mode.

## Deploying Dev

Requires AWS credentials with permission to create the resources in this
template, and SES-verified email addresses for `SesSenderEmail`,
`SesAdminRecipientEmail`, and each address in `SesAllowedTestRecipients`.

```bash
cd backend
sam build
sam deploy --config-env dev
```

`sam deploy --config-env dev` uses the parameter values in
`samconfig.toml` under `[dev.deploy.parameters]` — update the
`CHANGE_ME_*` placeholder email addresses to real, SES-verified
addresses before deploying.

## Local testing (no AWS deployment required)

```bash
cd backend
sam build
sam local invoke RegisterFunction --event events/register-event.json \
  --env-vars <(echo '{"RegisterFunction":{"TABLE_NAME":"local-table","SES_SENDER_EMAIL":"sender@example.com","SES_ADMIN_RECIPIENT_EMAIL":"admin@example.com","SES_ALLOWED_TEST_RECIPIENTS":"test.student@example.com","ENVIRONMENT_NAME":"dev"}}')
```

This will fail to actually reach DynamoDB/SES without valid AWS
credentials/resources, but confirms the handler code runs, parses the
event, and validates input correctly.

## Frontend integration (not applied yet)

The current production frontend (`js/main.js`) still calls the legacy
endpoint and is **not modified by this change**. Once the Dev API is
deployed and its generated endpoint URL is known, a follow-up change can
introduce hostname-based API base URL resolution so the same JS bundle
safely calls the Dev API on `dev.foma.life` and, later, the Production
API on `foma.life`.
